# A screen, from references to a checked render

**This holds for the whole task, not only the first build.** Every round that changes the screen, a correction included ("this button does nothing", "the hierarchy is weak"), ends the way the first one did, with the screen rendered in the Chrome DevTools MCP at the desktop and the phone width (the compare step) and its app shell (topbar, navigation, content margin) compared with the lead's next to the page body. A fix is not shown before that render and the control check below.

**The control check.** `take_snapshot` lists every button, link and menu item with its `uid`. Exercise each one with the MCP's `click` or `hover` on that `uid`, then read the page again (a fresh snapshot or a screenshot) to see that something changed: a click that changes nothing is an inert control. Once per round, also open and capture every modal, menu and tooltip, each hover state and each focused field, each state on its own beside the reference's, never as a before/after composite. `evaluate_script` reads state (layout, computed colour) and never clicks: `element.click()` fires the handler with no hit test, so a covered or dead control passes it (MDN `isTrusted`, Playwright actionability, read 2026-10-03).

The reply's first line names every control that does nothing and every width not rendered, so a stub is disclosed and never shipped silently; with nothing missing, it says nothing about it.

1. **Visual language**, before any reference is picked: what makes these screens this project's own. The default is the manual effort, whether or not the client has a site: with no visual language in the project and none brought, the turn ends per `devio:brand` on the brand reference images and the Lean prompt to paste, nothing built, no concept or layout described in prose and no token list, with "bring your own / skip the manual" in the same sentence. When the client has a site, the reply lists its logo, a capture of it and its colours (the values read from its CSS) as inputs to attach or hand to the design tool with the prompt, outside the prompt's own text. A reference the designer picked for how the screen is laid out gives structure, not language, and the reply does not describe it or say how the screen will be arranged: it waits for the build. **The exit** is the designer skipping the manual or bringing the language; the thread then builds in turn 1 from the first source that exists. (a) The approved brand manual, which is a visual language already brought: read as below, never answered with the manual effort again. (b) Else the designer's own reference: its colours and type. (c) Else the client's identity, read from the client's site with the Chrome DevTools MCP, not guessed: `new_page` on it, then `evaluate_script` (it reads, it never clicks) returning the custom properties, the `@font-face` list, and the computed `font-family`, `font-size`, `letter-spacing`, `text-transform` and colours of the hero, a label and the body. The client's identity gives colours, type family and logo, and nothing else: the structure is the lead's, the rest is product practice (Gotchas). Tag each token `[manual: slide label, position]`, `[site]`, with the property or selector it was read from, or `[derived]`, with what it was derived from; step 4 lists them in the reply, so the designer sees what each source gave and what was decided.

   **The manual as the language.** The screens take the manual's colours (brand, grounds, status scale), type family and logo, and its product foundations (screen type scale, spacing, radius, elevation, icon weights). Its graphic devices, voice and composition rules stay in the manual: a screen takes one only when the Lead page shows it in use. Open the PNG of each slide a token comes from with `Read` in this thread, never a summary of it, then check the value with `evaluate_script` on the export (`section[data-label]`, the computed colour, `font-family`, `font-size`, `letter-spacing`, `text-transform`): the printed value is the token and the computed one agrees to rounding. A mismatch goes in the reply with both values and the thread picks neither. A manual that arrives only as a PDF is read from its printed values, and the reply says the computed ones were not checked. The tag is the slide's `data-label` and its place in the deck, written in the reply exactly as `[manual: Colour, 2 of 7]`, brackets included, beside each token it traces (a phrase such as "slide 2" is not the tag); a token the manual lacks is `[derived]` and listed. With a manual and a site, the manual wins.

   **The manual wins over the translation Gotchas where it speaks;** they fill only what it leaves silent. A page that tracks its labels in capitals is built that way, and the reply names the departure from the Gotcha in one line that ends with the slide's literal `[manual: ...]` tag. A reserved colour the manual defines is named in the reply with its meaning and is not asked about: step 4's question is for a manual that is silent on it.
2. **References**, by the bar in `devio:references` (currency, the product's own world, tone, depth), searched only for a capability no open image shows. The designer's own, or found with the Mobbin MCP (`search_screens`, `search_flows`, `search_sections`) and the Firecrawl plugin (`firecrawl:firecrawl-scrape` with a screenshot, `firecrawl:firecrawl-search` to find the products). With neither at hand, or no tool to fetch them, the turn ends on asking the designer for them, with nothing built: a draft without references is not a start. Save each as an image and open it with Read; a chosen one may also be rebuilt as an HTML mockup, opened next to its image. Done when every reference the composition draws on is open in this thread.
3. **Lead,** for every screen, the first or a later one, from one ladder: (1) the brand manual's product page for the same surface, named in the reply with its title and its position in the deck, with no new approval; else (2) the project's closest approved screen, the Direction or a screen built since and accepted; else (3) the real product closest to this one's job, the one the designer named or else the closest found, with its UI references from step 2. A project with no manual starts at (2). A design-tool round is never reopened for one screen, and the ladder has no second flow. Follow the Lead the way a build told "make it like Apple" follows apple.com: its layout, density and hierarchy. Its colour and type are not the Lead's to give, they come from the visual language of step 1. The other references each supply one named part the Lead lacks. Two references that give the same part in opposite ways, with neither ranked by the designer, are no Lead to pick: that part is the question in step 6.
4. **First screen, in code.** Compose it yourself from the open images and the visual language, in the project's stack, with the product's real content. This screen is the direction. Show it to the designer and wait: the direction is theirs. The reply names, in order: the Lead page (its title and position in the deck, when it is the manual's), each token with its tag, each divergence from the Gotchas in one line, and what each other reference gave. Where alternatives are shown, they pass the Candidate test: swap the font, colour and radius between two; if they come out the same, they are one. When the identity has one reserved colour and the manual does not define it, the screen spends it on one meaning and the reply asks the designer which meaning it should have, with what each costs (Gotchas). The other routes then speak this screen's language.
5. **Motion** through the GSAP skills, and **every library** through context7.
6. **Compare and iterate.** At the end of a round, render with the Chrome DevTools MCP: `new_page` on the screen's URL, then per width an `emulate` and one `take_screenshot` — the reference's own size for desktop (as `1280x800x1`), `390x844x3,mobile,touch` for the phone. Not a script written on the spot and not a timer. Read each next to the references, image against image, fix what differs and go round again on your own until it matches. The loop ends as a question to the designer, with that part left unbuilt, when a difference survives two fix attempts, or when it needs a design decision: two references that disagree on a part and the designer ranked neither, or a part no reference shows. Name the difference, the options, and what each one trades. Do not pick for them and do not try a third time.
7. **Frame.** With more than one route, once after the screens match, measure the header height and the content's left edge on every route at phone and desktop widths with the Chrome DevTools MCP's `evaluate_script`. They match.
8. **Polish** with `impeccable:impeccable`, as a scoped command on the built code (`polish`, `critique`, `audit`), with the screen rendered in the Chrome DevTools MCP at both widths of step 6, then show the screen.

## Gotchas

- Impeccable composes nothing before step 8. Its new-work flow (`init`, `shape`, `craft`, a direction round with `concept-seed` and a decision page) draws its comps as its own images, not the designer's references, and rolls a visual world from its own catalog; it carries text cards only without image generation (`reference/new-work.md` and `visualize.md`, read 2026-10-04, Impeccable 4.3.1). On 2026-09-27 it set aside six open references for a roll, and the designer stopped the session as AI slop. A scoped command on existing code runs without `PRODUCT.md`: Impeccable's `context` says to proceed using the code and offer init as a suggestion (read 2026-09-27, Impeccable 4.3.1).
- Impeccable's `Stop` hook ("Design deep pass") reviews the written file when the turn ends and sends its findings back, so the turn's last reply becomes a lint report (Impeccable 4.3.1 `hooks/hooks.json`, read 2026-09-30). Handle the findings, then end that reply by showing the direction again as step 4 orders it (the lead, each token with its tag, each divergence, what each other reference gave) and the wait for the designer. The designer reads that last reply alone, so it carries all of step 4 again, with the reserved colour's meaning, and does not point back to an earlier message.
- No design skill composes better than this thread does from an open lead, and no polish skill finds what a render shows. In a bake-off on 2026-10-01 (Impeccable 4.4.0, frontend-design, ui-ux-pro-max 2.13.0, each against a session with no design skill), a named lead gave all four the same page. Polishing code without a render, ui-ux-pro-max kept its hero text touching the phone's edge. With the render, the session with no skill and each skill fixed all eight seeded defects. So steps 3–4 stay this thread's, and step 8 looks at the screen.
- A reference stays an image, or an HTML rebuild of one. A summary, a notes file, a direction card or a subagent's report loses the composition and the character, and a subagent's reply comes back as text only, so the thread that composes opens the references itself.
- The app shell (header, navigation) has one height on every route, and content starts at the same x. Titles, search, filters and metrics go in the page body. `html { scrollbar-gutter: stable }` keeps pages with and without a scrollbar aligned.
- Neither Impeccable's detector nor its reviewer compares routes, so step 7 is the only check of the frame.
- Impeccable's `critique` runs its two assessments as parallel subagents by its own rule, and the Chrome DevTools MCP serialises every call through one mutex, so they queue on one Chrome and a critique takes 14–15 minutes (timed 2026-10-02; Chrome DevTools MCP 1.9.0, Impeccable 4.3.1, read 2026-10-03). `--isolated` is per server, not per subagent, so a second Chrome per assessment is not available. Tell the designer this before the critique starts, in one line, so a quiet session is not read as a hung one, and leave the shared Chrome alone until both assessments return.
- Impeccable reads `.impeccable/config.json` from the current directory, not the git root (tested 2026-10-03, Impeccable 4.3.1). A suppression written from a worktree or a subfolder is ignored by a run started elsewhere: start the command in the folder that holds the config.
- On the emulated phone, a page wider than 390px is laid out wide and shrunk to fit, the way a phone paints it: no cut edge, only everything small over a long empty band. Read small type and empty space below the content as overflow, and confirm with `evaluate_script` comparing `document.documentElement.scrollWidth` to `clientWidth`; `innerWidth` grows with the page and reads 760 for a 760px page on a 390px phone (bake-off of 2026-10-01: Chrome DevTools MCP 1.9.0 won over Playwright MCP, whose window resize keeps desktop touch and hover, and over the desktop app's built-in browser, which is absent from headless runs and subagents).
- For a language read from a site or brought, and where the manual is silent: a client's site speaks to a visitor and a tool to someone in a task, so the site's habits are translated, not copied. Impeccable's Operate mode holds the product rules (restraint, density, display fonts out of labels, buttons and data, the accent for primary actions, selection and state), so they are not repeated here. It does not hold these three, each with its source (read 2026-10-03):
  - **Sentence case in the interface**, not uppercase with wide tracking: Carbon's writing style and Atlassian's language and grammar both set sentence case for titles, headings, labels and buttons.
  - **Page titles at 24–28px**: Atlassian sets 28 and 24px for page titles in apps and keeps 32 and 28px for marketing; macOS's largest title is 26pt (Apple HIG, Typography). A site's 64px display stays on the site.
  - **The brand's display type stays out of body text and data**: Apple allows a custom face for headlines with system fonts in the body, Atlassian keeps its brand face to marketing, and Material 3 warns against expressive faces for body text. They split on headlines, so the brand face goes on one title or marker at most.
- The reserved brand colour has no single meaning in the sources, so it is the designer's decision unless the manual defines it (read 2026-10-03). Atlassian reserves its brand role for primary actions, Apple's Branding page allows primary actions or status indicators, Shopify's strongest colour marks needs-attention, and Operate mode takes primary actions, selection and state. The first screen spends the colour on one meaning, and the reply names that meaning, the other, and what each costs: primary actions keep one clear path to act but leave nothing that shouts "now"; needs-attention makes the urgent row findable at a glance but leaves the primary action in a neutral colour.
- Firecrawl's `branding` format is not a source for the visual language. It has no field for tracking, case or surface steps, it is LLM-assisted (Firecrawl PR #2326, merged 2025-11-03, read with `gh api` on 2026-10-03), and it was wrong on a client's black site (a light scheme, confidence 0.925, 2026-10-02) and in a probe (text colour equal to the background on linear.app, 2026-10-03). Read the site's CSS with the Chrome DevTools MCP.
- A dense dark screen reads by planes, not by a grid of borders. Build the hierarchy from a neutral scale where each step has one job (Radix Colors: app background, panel, component at rest, hover and selected), about 4 L* between dark steps (Radix steps 1–6 sit 3.5–4.5 apart; Material 3's dark tones 4 to 24 sit 2–5 apart), a raised surface lighter, a well one step below its container. Borders stay for controls and focus: Material 3 asks for contrasting edges on interactive parts, and Linear softened its borders without dropping them (Radix docs, material-color-utilities `color_spec_2021.ts`, Linear's 2026 post, read 2026-10-03). The project's own values stay in that project.
