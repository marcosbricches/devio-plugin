# A screen, from references to a checked render

**This holds for the whole task, not only the first build.** Every round that changes the screen, a correction included ("this button does nothing", "the hierarchy is weak"), ends the way the first one did, with the screen rendered in the Chrome DevTools MCP at the desktop and the phone width (the compare step) and its app shell (topbar, navigation, content margin) compared with the lead's next to the page body. A fix is not shown before that render, and a control that was corrected is exercised in it with the MCP's `click` on its `take_snapshot` `uid`, never by a script: `element.click()` has no hit test, so a covered or dead control passes it (MDN `isTrusted`, Playwright actionability, read 2026-10-03). The reply's first line names any width not rendered; with nothing missing, it says nothing about it.

1. **References.** The designer's own, or found with the Mobbin MCP (`search_screens`, `search_flows`, `search_sections`) and the Firecrawl plugin (`firecrawl:firecrawl-scrape` with a screenshot, `firecrawl:firecrawl-search` to find the products). With no product named, search the product's own world: the apps its users already open for this job, and the boards, tables and objects of their trade. With neither at hand, or no tool to fetch them, the turn ends on asking the designer for them, with nothing built: a draft without references is not a start. Save each as an image and open it with Read; a chosen one may also be rebuilt as an HTML mockup, opened next to its image. Done when every reference the composition draws on is open in this thread.
2. **Lead.** Pick one open reference to lead: the one the designer named, or else the real product closest to this one's job. Follow it the way a build told "make it like Apple" follows apple.com: its layout, type scale, colour and density. The other references each supply one named part the lead lacks. Two references that give the same part in opposite ways, with neither ranked by the designer, are no lead to pick: that part is the question in step 5.
3. **First screen, in code.** Compose it yourself from the open images, in the project's stack, with the product's real content. This screen is the direction. Show it to the designer, naming the lead and what each other reference gave, and wait: the direction is theirs. The other routes then speak its language.
4. **Motion** through the GSAP skills, and **every library** through context7.
5. **Compare and iterate.** At the end of a round, render with the Chrome DevTools MCP: `new_page` on the screen's URL, then per width an `emulate` and one `take_screenshot` — the reference's own size for desktop (as `1280x800x1`), `390x844x3,mobile,touch` for the phone. Not a script written on the spot and not a timer. Read each next to the references, image against image, fix what differs and go round again on your own until it matches. The loop ends as a question to the designer, with that part left unbuilt, when a difference survives two fix attempts, or when it needs a design decision: two references that disagree on a part and the designer ranked neither, or a part no reference shows. Name the difference, the options, and what each one trades. Do not pick for them and do not try a third time.
6. **Frame.** With more than one route, once after the screens match, measure the header height and the content's left edge on every route at phone and desktop widths with the Chrome DevTools MCP's `evaluate_script`. They match.
7. **Polish** with `impeccable:impeccable`, as a scoped command on the built code (`polish`, `critique`, `audit`), with the screen rendered in the Chrome DevTools MCP at both widths of step 5, then show the screen.

## Gotchas

- Impeccable composes nothing before step 7. Its new-work flow (`init`, `shape`, `craft`, a direction round with `concept-seed` and a decision page) turns references into text cards and rolls a visual world from its own catalog. In a field trial on 2026-09-27 it set aside six open references for a roll, and the designer stopped the session as AI slop. A scoped command on existing code runs without `PRODUCT.md`: Impeccable's `context` says to proceed using the code and offer init as a suggestion (read 2026-09-27, Impeccable 4.3.1).
- Impeccable's `Stop` hook ("Design deep pass") reviews the written file when the turn ends and sends its findings back, so the turn's last reply becomes a lint report (Impeccable 4.3.1 `hooks/hooks.json`, read 2026-09-30). Handle the findings, then end that reply by showing the direction again: the lead, what each other reference gave, and the wait for the designer.
- No design skill composes better than this thread does from an open lead, and no polish skill finds what a render shows. In a bake-off on 2026-10-01 (Impeccable 4.4.0, frontend-design, ui-ux-pro-max 2.13.0, each against a session with no design skill), a named lead gave all four the same page. Polishing code without a render, ui-ux-pro-max kept its hero text touching the phone's edge. With the render, the session with no skill and each skill fixed all eight seeded defects. So steps 2–3 stay this thread's, and step 7 looks at the screen.
- A reference stays an image, or an HTML rebuild of one. A summary, a notes file, a direction card or a subagent's report loses the composition and the character, and a subagent's reply comes back as text only, so the thread that composes opens the references itself.
- The app shell (header, navigation) has one height on every route, and content starts at the same x. Titles, search, filters and metrics go in the page body. `html { scrollbar-gutter: stable }` keeps pages with and without a scrollbar aligned.
- Neither Impeccable's detector nor its reviewer compares routes, so step 6 is the only check of the frame.
- Impeccable's `critique` runs its two assessments as parallel subagents by its own rule, and the Chrome DevTools MCP serialises every call through one mutex, so they queue on one Chrome and a critique takes 14–15 minutes (field trial of 2026-10-02; Chrome DevTools MCP 1.9.0, Impeccable 4.3.1, read 2026-10-03). `--isolated` is per server, not per subagent, so a second Chrome per assessment is not available. Tell the designer this before the critique starts, in one line, so a quiet session is not read as a hung one, and leave the shared Chrome alone until both assessments return.
- Impeccable reads `.impeccable/config.json` from the current directory, not the git root (tested 2026-10-03, Impeccable 4.3.1). A suppression written from a worktree or a subfolder is ignored by a run started elsewhere: start the command in the folder that holds the config.
- On the emulated phone, a page wider than 390px is laid out wide and shrunk to fit, the way a phone paints it: no cut edge, only everything small over a long empty band. Read small type and empty space below the content as overflow, and confirm with `evaluate_script` comparing `document.documentElement.scrollWidth` to `clientWidth`; `innerWidth` grows with the page and reads 760 for a 760px page on a 390px phone (bake-off of 2026-10-01: Chrome DevTools MCP 1.9.0 won over Playwright MCP, whose window resize keeps desktop touch and hover, and over the desktop app's built-in browser, which is absent from headless runs and subagents).
