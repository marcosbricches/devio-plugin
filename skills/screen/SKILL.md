# A screen, from references to a checked render

**This holds for the whole task, not only the first build.** Every round that changes the screen, a correction included ("this button does nothing", "the hierarchy is weak"), ends the way the first one did, with the screen rendered in the Chrome DevTools MCP at the desktop and the phone width (the compare step) and its app shell (topbar, navigation, content margin) compared with the lead's next to the page body. A fix is not shown before that render, and a control that was corrected is exercised in it with the MCP's `click` on its `take_snapshot` `uid`, never by a script: `element.click()` has no hit test, so a covered or dead control passes it (MDN `isTrusted`, Playwright actionability, read 2026-10-03). The reply's first line names any width not rendered; with nothing missing, it says nothing about it.

1. **Visual language**, before any reference is picked: what makes these screens this project's own. It comes from the first source that exists. (a) The designer's own reference: its colours and type. (b) Else the client's identity, read from the client's site with the Chrome DevTools MCP, not guessed: `new_page` on it, then `evaluate_script` (it reads, it never clicks) returning the custom properties, the `@font-face` list, and the computed `font-family`, `font-size`, `letter-spacing`, `text-transform` and colours of the hero, a label and the body. (c) Else the turn ends on asking the designer where the language comes from, with nothing built. The client's identity gives colours, type family and logo, and nothing else: the structure is the lead's, the rest is product practice (Gotchas). Write each token down tagged `[site]`, with the property or selector it was read from, or `[derived]`, with what it was derived from.
2. **References.** The designer's own, or found with the Mobbin MCP (`search_screens`, `search_flows`, `search_sections`) and the Firecrawl plugin (`firecrawl:firecrawl-scrape` with a screenshot, `firecrawl:firecrawl-search` to find the products). With no product named, search the product's own world: the apps its users already open for this job, and the boards, tables and objects of their trade. With neither at hand, or no tool to fetch them, the turn ends on asking the designer for them, with nothing built: a draft without references is not a start. Save each as an image and open it with Read; a chosen one may also be rebuilt as an HTML mockup, opened next to its image. Done when every reference the composition draws on is open in this thread.
3. **Lead.** Pick one open reference to lead: the one the designer named, or else the real product closest to this one's job. Follow it the way a build told "make it like Apple" follows apple.com: its layout, density and hierarchy. Its colour and type are not the lead's to give, they come from the visual language of step 1. The other references each supply one named part the lead lacks. Two references that give the same part in opposite ways, with neither ranked by the designer, are no lead to pick: that part is the question in step 6.
4. **First screen, in code.** Compose it yourself from the open images and the visual language, in the project's stack, with the product's real content. This screen is the direction. Show it to the designer, naming where the visual language came from, the lead and what each other reference gave, and wait: the direction is theirs. When the client's identity has one reserved colour, the screen spends it on one meaning and the reply asks the designer which meaning it should have, with what each costs (Gotchas). The other routes then speak this screen's language.
5. **Motion** through the GSAP skills, and **every library** through context7.
6. **Compare and iterate.** At the end of a round, render with the Chrome DevTools MCP: `new_page` on the screen's URL, then per width an `emulate` and one `take_screenshot` — the reference's own size for desktop (as `1280x800x1`), `390x844x3,mobile,touch` for the phone. Not a script written on the spot and not a timer. Read each next to the references, image against image, fix what differs and go round again on your own until it matches. The loop ends as a question to the designer, with that part left unbuilt, when a difference survives two fix attempts, or when it needs a design decision: two references that disagree on a part and the designer ranked neither, or a part no reference shows. Name the difference, the options, and what each one trades. Do not pick for them and do not try a third time.
7. **Frame.** With more than one route, once after the screens match, measure the header height and the content's left edge on every route at phone and desktop widths with the Chrome DevTools MCP's `evaluate_script`. They match.
8. **Polish** with `impeccable:impeccable`, as a scoped command on the built code (`polish`, `critique`, `audit`), with the screen rendered in the Chrome DevTools MCP at both widths of step 6, then show the screen.

## Gotchas

- Impeccable composes nothing before step 8. Its new-work flow (`init`, `shape`, `craft`, a direction round with `concept-seed` and a decision page) turns references into text cards and rolls a visual world from its own catalog. In a field trial on 2026-09-27 it set aside six open references for a roll, and the designer stopped the session as AI slop. A scoped command on existing code runs without `PRODUCT.md`: Impeccable's `context` says to proceed using the code and offer init as a suggestion (read 2026-09-27, Impeccable 4.3.1).
- Impeccable's `Stop` hook ("Design deep pass") reviews the written file when the turn ends and sends its findings back, so the turn's last reply becomes a lint report (Impeccable 4.3.1 `hooks/hooks.json`, read 2026-09-30). Handle the findings, then end that reply by showing the direction again: the lead, what each other reference gave, and the wait for the designer.
- No design skill composes better than this thread does from an open lead, and no polish skill finds what a render shows. In a bake-off on 2026-10-01 (Impeccable 4.4.0, frontend-design, ui-ux-pro-max 2.13.0, each against a session with no design skill), a named lead gave all four the same page. Polishing code without a render, ui-ux-pro-max kept its hero text touching the phone's edge. With the render, the session with no skill and each skill fixed all eight seeded defects. So steps 3–4 stay this thread's, and step 8 looks at the screen.
- A reference stays an image, or an HTML rebuild of one. A summary, a notes file, a direction card or a subagent's report loses the composition and the character, and a subagent's reply comes back as text only, so the thread that composes opens the references itself.
- The app shell (header, navigation) has one height on every route, and content starts at the same x. Titles, search, filters and metrics go in the page body. `html { scrollbar-gutter: stable }` keeps pages with and without a scrollbar aligned.
- Neither Impeccable's detector nor its reviewer compares routes, so step 7 is the only check of the frame.
- Impeccable's `critique` runs its two assessments as parallel subagents by its own rule, and the Chrome DevTools MCP serialises every call through one mutex, so they queue on one Chrome and a critique takes 14–15 minutes (field trial of 2026-10-02; Chrome DevTools MCP 1.9.0, Impeccable 4.3.1, read 2026-10-03). `--isolated` is per server, not per subagent, so a second Chrome per assessment is not available. Tell the designer this before the critique starts, in one line, so a quiet session is not read as a hung one, and leave the shared Chrome alone until both assessments return.
- Impeccable reads `.impeccable/config.json` from the current directory, not the git root (tested 2026-10-03, Impeccable 4.3.1). A suppression written from a worktree or a subfolder is ignored by a run started elsewhere: start the command in the folder that holds the config.
- On the emulated phone, a page wider than 390px is laid out wide and shrunk to fit, the way a phone paints it: no cut edge, only everything small over a long empty band. Read small type and empty space below the content as overflow, and confirm with `evaluate_script` comparing `document.documentElement.scrollWidth` to `clientWidth`; `innerWidth` grows with the page and reads 760 for a 760px page on a 390px phone (bake-off of 2026-10-01: Chrome DevTools MCP 1.9.0 won over Playwright MCP, whose window resize keeps desktop touch and hover, and over the desktop app's built-in browser, which is absent from headless runs and subagents).
- A client's site speaks to a visitor and a tool to someone in a task, so the site's habits are translated, not copied. Impeccable's Operate mode holds the product rules (restraint, density, display fonts out of labels, buttons and data, the accent for primary actions, selection and state), so they are not repeated here. It does not hold these three, each with its source (read 2026-10-03):
  - **Sentence case in the interface**, not uppercase with wide tracking: Carbon's writing style and Atlassian's language and grammar both set sentence case for titles, headings, labels and buttons.
  - **Page titles at 24–28px**: Atlassian sets 28 and 24px for page titles in apps and keeps 32 and 28px for marketing; macOS's largest title is 26pt (Apple HIG, Typography). A site's 64px display stays on the site.
  - **The brand's display type stays out of body text and data**: Apple allows a custom face for headlines with system fonts in the body, Atlassian keeps its brand face to marketing, and Material 3 warns against expressive faces for body text. They split on headlines, so the brand face goes on one title or marker at most.
- The reserved brand colour has no single meaning in the sources, so it is the designer's decision (read 2026-10-03). Atlassian reserves its brand role for primary actions, Apple's Branding page allows primary actions or status indicators, Shopify's strongest colour marks needs-attention, and Operate mode takes primary actions, selection and state. The first screen spends the colour on one meaning, and the reply names that meaning, the other, and what each costs: primary actions keep one clear path to act but leave nothing that shouts "now"; needs-attention makes the urgent row findable at a glance but leaves the primary action in a neutral colour.
- Firecrawl's `branding` format is not a source for the visual language. It has no field for tracking, case or surface steps, it is LLM-assisted (Firecrawl PR #2326, merged 2025-10-28), and it was wrong in the Monster Films trial (a light scheme for a black site, confidence 0.925, 2026-10-02) and in a probe (text colour equal to the background on linear.app, 2026-10-03). Read the site's CSS with the Chrome DevTools MCP.
- A dense dark screen reads by planes, not by a grid of borders. Build the hierarchy from a neutral scale where each step has one job (Radix Colors: app background, panel, component at rest, hover and selected), about 4 L* between dark steps (Radix steps 1–6 sit 3.5–4.5 apart; Material 3's dark tones 4 to 24 sit 2–5 apart), a raised surface lighter, a well one step below its container. Borders stay for controls and focus: Material 3 asks for contrasting edges on interactive parts, and Linear softened its borders without dropping them (Radix docs, material-color-utilities `color_spec_2021.ts`, Linear's 2026 post, read 2026-10-03). The project's own values stay in that project.
